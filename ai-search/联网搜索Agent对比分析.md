# 联网搜索 Agent 对比分析

## 两种方案概览

| | 火山引擎联网问答 Agent | 自建联网搜索 Agent（poipoi-agent） |
|---|---|---|
| 架构模式 | 服务端编排（全托管黑盒） | 客户端编排（完全透明） |
| 接口 | 一个 HTTP API 搞定 | LLM API + 搜索 API + 网页抓取，自己编排 |
| 工具调用 | 后端内部完成，不可见 | Function Calling，参数/返回值全透明 |
| 同问题耗时 | **~2.3s** | **~4.05s** |

## 火山引擎的具体实现分析

### 请求流程

```
客户端 → POST /agent_api/agent/chat/completion
         {bot_id, messages, stream: true}

火山后端（黑盒）:
  ├─ planning        → 意图识别 + 查询改写（智能改写 ON）
  ├─ tools_begin     → 并行调用内置工具（世界时钟/计算器/万年历等）
  ├─ search_begin    → 并行调用多搜索源（联网资源+头条+抖音百科+墨迹天气）
  ├─ search_finish   → 搜索结果聚合（最多30条 search_results）
  ├─ tools_finish    → 工具结果汇总
  ├─ tools_decision  → 采纳工具结论
  └─ 总结生成        → 将搜索结果注入 prompt，模型生成回复

客户端 ← SSE 流式响应
         首帧: references + search_results + cards
         中间帧: content（逐字输出）
         尾帧: finish_reason=stop
         元数据帧: follow_ups + usage
         结束帧: [DONE]
```

### 关键设计细节

**1. 搜索源并行 + 工具并行**

从 processing_state 帧的时序可以看出，`tools_begin` 和 `search_begin` 几乎同时触发。火山后端对多个搜索源（搜索引擎、头条文章、抖音百科、墨迹天气）以及内置工具（世界时钟等）做了并行调用，而不是串行等待。这是它快的核心原因。

**2. 智能改写（Query Rewriting）**

控制台开启了"智能改写"，Agent 会先把用户原始问题改写成更适合搜索引擎的 query。比如用户问"现在几点了"，可能被改写为"当前北京时间"。这一步消耗额外 token 但提升搜索质量。

**3. RAG 注入方式**

搜索完成后，火山后端将搜索结果摘要拼接到 system prompt 中喂给大模型。从 token 用量可以验证：
- 用户只发了一句话（几个 token）
- prompt_tokens 高达 3163~8007
- 差值就是搜索结果上下文 + 系统指令

**4. 工具调用不透传**

虽然后端调用了世界时钟等工具，但 `tool_calls` 字段不会返回给客户端。客户端只能通过 `processing_state` 知道"用了工具"这个事实，看不到具体调了什么函数、传了什么参数、返回了什么。

**5. 引用条数控制**

控制台设置引用上限为 10 条。实际搜索可能返回 30 条 `search_results`，但 `references`（模型实际引用的）最多 9~10 条。说明模型会从搜索结果中筛选最相关的进行引用。

### 响应帧结构

```
帧类型          内容                              出现时机
─────────────────────────────────────────────────────────
处理状态帧      processing_state (action+desc)    开启 enable_processing_state 时
内容首帧        references + search_results + cards 总结开始
内容中间帧      delta.content (逐字)               总结过程中
内容尾帧        finish_reason=stop                 总结结束
元数据帧        follow_ups + usage                 总结结束后
结束帧          data:[DONE]                        最后一帧
```

## 自建方案的实现

### 工作流

```
IntentNode（LLM + Function Calling）
  ├─ tool_call → ToolCallNode（执行搜索/抓取/时间查询）→ 回到 IntentNode
  └─ output   → OutputNode（输出最终回复）
```

### 耗时分解（约 4.05s）

```
IntentNode #1: LLM 判断意图 + 决定调工具    ~1.5s
ToolCallNode:  DuckDuckGo 搜索              ~1.0s
IntentNode #2: LLM 基于搜索结果生成回复      ~1.5s
─────────────────────────────────────────────
总计                                         ~4.0s
```

核心瓶颈：**两次 LLM 调用是串行的**（第一次判断意图，第二次生成回复），且搜索也是串行等待。

## 性能差距原因

| 因素 | 火山引擎 (~2.3s) | 自建方案 (~4.05s) |
|---|---|---|
| LLM 调用次数 | 可能 1 次（意图+总结合并） | 2 次串行（意图 → 总结） |
| 搜索并行度 | 多源并行 | 单源串行（DuckDuckGo） |
| 工具调用 | 与搜索并行 | 串行等待 |
| 基础设施 | 内网低延迟，专用集群 | 公网调用第三方 API |
| 模型 | 自研/优化模型 | Qwen3.5-397B（第三方） |

### 火山快在哪

1. **并行化**：搜索、工具调用、意图判断可能在后端流水线化执行，减少串行等待
2. **内网通信**：搜索引擎和 LLM 都在火山内部，网络延迟极低
3. **模型优化**：可能使用针对搜索场景微调的小模型做意图判断，大模型只做最终总结
4. **预热/缓存**：热门查询可能有结果缓存，搜索引擎有预建索引

### 自建方案可优化方向

1. 搜索和意图判断并行（先搜索，同时让 LLM 判断）
2. 使用更快的搜索 API（Bing/Google API 替代 DuckDuckGo）
3. 换用更快的 LLM（小模型做意图，大模型做总结）
4. 加搜索结果缓存

### 火山引擎 Token 消耗分析

火山引擎的 input token 远高于用户实际输入，构成如下：

```
用户输入:     ~10 token
系统指令:     ~500 token（估算，含 system prompt + 格式要求）
搜索结果注入: ~7,200 token（30条搜索结果的标题+摘要）
─────────────────────────────
总 input:     7,724 token
```

这意味着约 93% 的 input token 是搜索结果上下文，用户实际输入占比不到 1%。这是 RAG 模式的典型特征：用大量检索内容换取回答的准确性和时效性。

### 关键发现

1. **火山的搜索覆盖面远超自建方案**：30 条多源结果 vs 8 条 DuckDuckGo 结果，信息密度差距明显
2. **火山只需 1 次 LLM 调用**：后端将意图判断、搜索、总结合并在一次模型推理中完成（或用小模型做前置判断），自建方案需要 2 次串行 LLM 调用
3. **Token 消耗主要来自搜索结果注入**：两种方案的 token 消耗量级相近，说明搜索结果上下文是主要开销
4. **流式输出体验更好**：火山的 408 帧逐字输出让用户感知延迟更低，即使总耗时 6.98s 也不觉得慢

### 火山引擎 Token 构成模型

通过三种场景的对比，可以推算出火山 Agent 的 token 构成：

| 场景 | input token | 系统指令（固定） | 搜索/工具结果（动态） |
|---|---|---|---|
| "你好"（闲聊） | 1,195 | ~1,195 | 0 |
| "现在几点了"（工具调用） | 3,163 | ~1,195 | ~1,968 |
| "周杰伦最新消息"（联网搜索） | 7,724 | ~1,195 | ~6,529 |

结论：
- 火山 Agent 的**固定开销约 1,200 token**（系统指令 + 格式要求 + 工具描述），这是每次请求的"底噪"
- 搜索结果注入的 token 量与问题复杂度正相关：简单工具查询 ~2,000，复杂搜索 ~6,500
- 即使是"你好"这样的闲聊，也需要 3 秒响应，说明 Agent 后端的 planning 阶段有固定延迟（意图识别 + 路由决策）

### 火山引擎四种工作流路径

```
用户输入
  │
  ▼
planning（意图识别）
  │
  ├─ 闲聊 ──────────────────────────→ 直接生成回复
  │                                    (planning → processing_finish)
  │
  ├─ 需要搜索 ──→ search_begin ──→ search_finish ──→ 生成回复
  │                                    (planning → search → processing_finish)
  │
  ├─ 需要工具 ──→ tools_begin ──→ tools_finish ──→ 生成回复
  │                                    (planning → tools → processing_finish)
  │
  └─ 需要工具+搜索 ──→ tools_begin ──→ search_begin ──→ search_finish
                        ──→ tools_finish ──→ tools_decision ──→ 生成回复
                        (planning → tools+search 并行 → processing_finish)
```

### 火山引擎多轮对话的上下文管理

关键发现：传入 13 条消息，input token 仅 1,846。对比单条"你好"（无历史）的 1,195 token，多了 13 条消息只增加了 ~650 token。原因：

1. **消息截断机制**：根据文档，火山引擎最多使用传入的 10 条消息。超过 10 条只保留最后 10 条（如果第一条是 system 类型则始终保留）。13 条消息实际只用了最后 10 条。

2. **无压缩，原文传入**：经自动化测试验证（见压缩测试章节），历史消息原文传入模型，每轮精确增加 44 token，完全线性增长。

3. **回忆能力验证**：Agent 正确回忆了之前问过的三个不同问题（现在几点、周杰伦最新消息、你好），说明 10 条消息窗口足够覆盖近期对话历史。

### 多轮对话 Token 增长模型

| 消息条数 | input token | 增量 | 说明 |
|---|---|---|---|
| 1 条（"你好"，无历史） | 1,195 | — | 基线：系统指令 ~1,195 |
| 13 条（7轮对话） | 1,846 | +651 | 实际只用最后 10 条 |

结论：火山引擎的多轮对话 token 增长是受控的，不会因为对话轮数增加而线性膨胀，10 条消息上限是硬性约束。

### 多轮对话 Token 增长对比（修正版）

两次测试虽然都是 13 条消息，但对话内容不同，token 差异反映的是历史内容长度的差别：

| 测试 | 消息数 | input token | 历史内容特征 |
|---|---|---|---|
| 第一次 | 13 条 | 1,846 | 简短对话：你好、时间查询、周杰伦（回复较短） |
| 第二次 | 13 条 | 4,226 | 丰富对话：含周杰伦长文、天气对比、美食推荐、复合问题 |

注意：两次的 13 条消息内容完全不同，不能直接对比得出"压缩"结论。

结论：
- input token 主要取决于历史消息的总文本长度，而非消息条数
- 10 条消息上限是条数限制，不是 token 限制
- 包含长回复（如周杰伦动态、美食推荐）的历史会显著增加 input token

### 语义理解观察

Agent 回答"你刚刚依次提出了三个要求"，对应的是上一轮的复合问题"帮我看几点了、查杭州天气、看周杰伦消息"，而非整个会话的所有问题。说明模型正确理解了"刚刚"指代上一轮对话，而非整个会话历史。


### 压缩测试：火山引擎是否对历史消息做压缩？

测试方法：使用相同的固定对话模板（user 约30字 + assistant 约40字），逐步增加轮数，观察 input token 增长。

```
测试脚本: test_token_growth.py
每轮模板:
  user: "请用一句话介绍一下Python语言的特点"
  assistant: "Python是一种简洁易读、功能强大的高级编程语言，以其丰富的库生态和广泛的应用场景著称。"
最后追加: user "你好"
```

| 轮数 | 消息数 | input token | 增量 | 耗时 |
|---|---|---|---|---|
| 0 | 1 | 659 | — | 3.23s |
| 1 | 3 | 703 | +44 | 3.14s |
| 2 | 5 | 747 | +44 | 2.32s |
| 3 | 7 | 791 | +44 | 2.87s |
| 4 | 9 | 835 | +44 | 2.55s |
| 5 | 11 | 866 | +31 | 2.00s |

结论：

1. **未做压缩**：0~4 轮（1~9 条消息），每增加 1 轮精确增加 44 token，完全线性增长，说明历史消息原文传入模型，没有做摘要压缩
2. **确认 10 条截断**：第 5 轮（11 条消息）增量从 44 降到 31，因为最早的 1 条消息被丢弃（只保留最后 10 条），增量 = 新增 44 - 被丢弃 ~13 ≈ 31
3. **基线系统指令约 659 token**（非流式请求），比浏览器流式请求的 1195 少，可能是因为流式模式额外包含 processing_state 相关指令


### 截断机制实证：超过 10 条消息后的行为

#### 测试 1：15 条消息 → "2+4等于多少"

| 指标 | 数据 |
|---|---|
| 传入消息数 | 15 条 |
| input token | 7,121 |
| 工作流 | planning → tools_begin → tools_finish → processing_finish（调用计算器） |
| 耗时 | 3.00s |

#### 测试 2：17 条消息 → "我第一句给你说的话是什么"

| 指标 | 数据 |
|---|---|
| 传入消息数 | 17 条 |
| input token | 3,076（比 15 条时的 7,121 大幅下降） |
| 工作流 | planning → processing_finish（直接回复） |
| 耗时 | 3.46s |
| 回答 | ❌ 错误！回答"杭州市明天更热..."，实际第一句是"你好" |

#### 分析

1. **10 条截断实锤**：17 条消息只保留最后 10 条（第 8~17 条），"你好"（第 1 条）已被丢弃，所以 Agent 无法正确回忆第一句话

2. **token 大幅下降的原因**：15 条→17 条时，截断窗口滑动，周杰伦长回复（约 600 字）和美食推荐长回复被移出窗口，导致 input token 从 7121 降到 3076

3. **截断窗口内容推算**：
   ```
   15 条消息，保留第 6~15 条：
     [6] assistant: 美食推荐（长文）
     [7] user: 复合问题（时间+天气+周杰伦）
     [8] assistant: 时间+天气+周杰伦回复（长文）
     ...
     → input token: 7,121（包含两段长回复）

   17 条消息，保留第 8~17 条：
     [8] assistant: 时间+天气+周杰伦回复（长文）
     [9] user: 我刚刚问你什么了
     [10] assistant: 三个要求（短回复）
     ...
     → input token: 3,076（美食长回复被丢弃）
   ```

4. **计算器工具调用**："2+4" 触发了 `tools_begin → tools_finish`（无 search），确认计算器是独立于搜索的内置工具
